# Implementation Phases

## Phase 0: Decisions And Boundaries
Deliverables:
- Confirm the strict four-table schema:
  - `import_workspaces`
  - `import_rows`
  - `import_candidates`
  - `import_commit_ledger`
- Confirm inactive-student invariant.
- Confirm first supported file types: CSV and XLSX.
- Confirm Phase 1 entity scope: active students, inactive archive, guardians, services, notes.
- Confirm import execution model: frontend parsing plus client-orchestrated chunks under the SWA 30-second timeout.
- Confirm initial CSV encoding policy: frontend auto-detects UTF-8/UTF-8-BOM/Windows-1255 with manual override.
- Confirm raw file retention policy: upload originals to Cloudflare R2 with pre-signed URLs and a 30-day lifecycle TTL.
- Confirm Phase 1 chunk size defaults:
  - 500 rows per row ingestion request
  - 100 candidates per analyze/dry-run/commit request
  - reduce chunk size automatically if endpoint timing approaches 30 seconds

Non-goals:
- No extra import metadata tables in Phase 1.
- No historical finance commit.
- No activation of historical attendance into live attendance, billing, or payroll state.
- No direct document upload migration.
- No fully automated "fix everything" mode.
- No destructive Undo button until post-import mutation checks exist.

## Phase 1: Four-Table Staging Foundation
Deliverables:
- Add the four import tables to `src/lib/setup-sql.js`.
- Add RLS and indexes.
- Add `CHECK` constraints for workspace/candidate/entity/action statuses.
- Add `ON DELETE CASCADE` workspace foreign keys so deleting a workspace removes all staged data and ledger rows.
- Add API routes:
  - `POST /api/import-workspaces`
  - `GET /api/import-workspaces`
  - `GET /api/import-workspaces/:id`
  - `PATCH /api/import-workspaces/:id`
  - `POST /api/import-workspaces/:id/rows:bulk`
  - `POST /api/import-workspaces/:id/analyze-chunk`
  - `POST /api/import-workspaces/:id/dry-run/chunk`
  - `POST /api/import-workspaces/:id/commit/chunk`
- Store file metadata, sheet metadata, encodings, mappings, and progress in `import_workspaces.config`.
- Store temporary R2 object keys and expected expiry timestamps in `import_workspaces.config`.
- Store frontend-parsed row JSON in `import_rows.raw_data`.

Validation:
- `npm run lint:sql`
- `npm run lint:api`

## Phase 2: Frontend Parsing And Normalization
Deliverables:
- Browser-side CSV/XLSX parsing using SheetJS/PapaParse.
- Direct browser upload of original files to Cloudflare R2 using pre-signed URLs.
- R2 originals are retained for debugging only and auto-delete after 30 days.
- Browser-side encoding detection and override:
  - `utf-8`
  - `utf-8-sig`
  - `windows-1255`
  - `windows-1252`
  - `unknown`
- Browser-side row profiling:
  - file name
  - sheet name
  - row count
  - header candidates
  - empty columns
  - likely entity type
- Aggressive pre-mapping normalization:
  - strip non-numeric characters from phone and identity values
  - normalize safe dates to ISO
  - preserve raw date values when ambiguous
  - trim strings
  - normalize common Hebrew punctuation variants
- Store normalization warnings inside each row's `raw_data`.
- Write file/sheet/profile/mapping state to `import_workspaces.config`.
- Generate unique `source_reference` values by appending a timestamp or content hash, for example `students.xlsx_1715694200`. Re-uploading a corrected file with the same original name must produce a different `source_reference`.

First alias set:
- first name: `שם פרטי`, `שם`, `first_name`, `first name`
- last name: `שם משפחה`, `משפחה`, `last_name`, `last name`
- identity: `ת.ז`, `תעודת זהות`, `מספר זהות`, `identity`, `id_number`
- phone: `טלפון`, `נייד`, `פלאפון`, `phone`, `mobile`
- email: `אימייל`, `מייל`, `email`
- status: `סטטוס`, `פעיל`, `active`, `status`
- guardian name: `שם הורה`, `שם אפוטרופוס`, `guardian`
- service: `שירות`, `טיפול`, `service`
- notes: `הערות`, `notes`

## Phase 3: Row Ingestion
Deliverables:
- `POST /api/import-workspaces/:id/rows:bulk`
- Accept rows shaped like:

```json
{
  "source_reference": "legacy.xlsx#Students_1715694200",
  "rows": [
    {
      "row_index": 1,
      "raw_data": {
        "raw": {},
        "normalized": {},
        "warnings": []
      }
    }
  ]
}
```

Backend requirements:
- Validate auth and membership.
- Resolve `org_id` from request/body.
- Enforce chunk size.
- Reject mixed workspace/source chunks.
- Insert rows idempotently using `(workspace_id, source_reference, row_index)`.
- Require `source_reference` to include a timestamp/hash suffix generated by the frontend. This prevents fixed filenames from colliding when users re-upload corrected files.
- Do not create candidates or live records during row ingestion.

## Phase 4: Candidate Analyzer
Deliverables:
- `POST /api/import-workspaces/:id/analyze-chunk`
- Convert rows into `import_candidates`.
- Build Golden Records by merging duplicate rows into one candidate when confident or user-approved.
- Populate:
  - `entity_type`
  - `candidate_data`
  - `merged_from_row_ids`
  - `issues`
  - `blocking_issues_count`
  - `decisions`
  - `depends_on_candidate_id`
- Use `depends_on_candidate_id` for simple Phase 1 dependency blocking.
- Mark downstream candidates `blocked_by_dependency` when their parent candidate is blocked or not committed/ready.

Candidate rules:
- `customer` represents both active/inactive students and one-time customers.
- `guardian_link` depends on the related student candidate.
- `guardian` can stand alone unless a link is being committed.
- `instructor` may link to an existing instructor or create an unlinked overlay.
- `lesson` resolves a committed/existing instructor and service.
- `lesson_participant` resolves a committed/existing lesson and identified client profile.

Inactive archive rule:
- inactive candidates with `blocking_issues_count > 0` remain staged
- inactive candidates with unresolved conflicts remain staged
- inactive candidates require first name, last name, and a valid identity number
- inactive student candidates require either a valid student phone or a linked guardian
  with a valid phone or email; student email alone is not a valid contact path
- upstream corrections may be re-uploaded, and missed exceptions may be repaired in the
  Import Workspace; both paths must be re-analyzed before commit
- no inactive candidate mutates live tables before commit

Deliverables:

- Workspace detail dashboard.
- Upload/parser panel.
- Mapping panel.
- Review queues from `import_candidates`.
- Candidate detail drawer showing:
  - merged source rows
  - normalized values
  - issues
  - decisions
  - dependency parent
  - dry-run preview from `candidate_data`
- Decision actions:
  - link to existing
  - create as new
  - skip
  - edit normalized value
  - map service
  - resolve duplicate

UX requirements:
- show progress by queue, not just total rows
- support "continue later"
- make active and inactive lanes visually separate
- make inactive archive commit language explicit and careful

- show dependency-blocked candidates as waiting on another candidate

## Phase 6: Dry Run Engine
Deliverables:
- `POST /api/import-workspaces/:id/dry-run/chunk`
- Accept bounded candidate IDs.
- Re-check candidate status, issues, conflicts, and dependency state.
- Write dry-run result summaries into `import_candidates.candidate_data.dry_run`.
- Update operation progress in `import_workspaces.config`.

Important:
- Dry run must not mutate live tables.
- Dry run must be repeatable after mapping or decisions change.
- Dry run chunks must reject inactive candidates with unresolved blocking issues, unresolved conflicts, or missing archive fields.

## Phase 7: Commit Engine
Deliverables:
- `POST /api/import-workspaces/:id/commit/chunk`
- Accept bounded candidate IDs.
- Use existing domain helpers for live writes where possible:
  - `createOrReuseClientProfile`
  - `ensureStudentForClientProfile`
  - `createOrReuseGuardian`
  - `upsertClientGuardianLink`
  - existing student validation helpers
- Write provenance metadata to live records.
- Write `import_commit_ledger` rows for each live create/update/link.
- Mark committed candidates as `committed`.

Backend commit requirement (superseded by `commit-engine-revision.md`):
- Use the per-candidate idempotent JavaScript orchestrator so imports reuse the same domain helpers and non-destructive merge behavior as interactive creation.
- The API validates auth, membership, `org_id`, workspace ownership, chunk size, and requested candidate IDs.
- Before each write, re-check that the candidate is committable, has no blockers, and has a satisfied dependency.
- Record every create, update, or link in `import_commit_ledger`.
- A row failure is retained as retryable import state and does not roll back unrelated successful rows.
- Idempotent source identifiers and live-record lookups make a retried chunk safe after partial success.

Frontend topological order requirement:
- The frontend orchestrator must query and commit chunks by entity type in dependency order.
- Commit `customer` first.
- Commit `guardian`, `service`, and `instructor` next.
- Commit `guardian_link` and `lesson` after their lookup resources exist.
- Commit `lesson_participant` last.
- If any earlier entity type has failed or blocked candidates, dependent entity types must pause and surface the blockers.
- This order is mandatory even though the backend also re-checks `depends_on_candidate_id`.

Inactive archive commit:
- selected inactive students use `entity_type = 'customer'`, `customer_type = 'student'`, and `is_active = false`
- selected inactive candidates must have `status = 'ready'`
- selected inactive candidates must have `blocking_issues_count = 0`
- selected inactive candidates must have no unresolved conflicts in `candidate_data.field_conflicts`
- selected inactive candidates must pass minimum archive field validation
- committed inactive students are created inactive immediately
- no schedules, billing, forms, document requirements, or operational side effects are created

## Phase 8: Operational Hardening
Deliverables:
- Import activity summary from `import_workspaces.config`.
- Dashboard task integration for unresolved import work.
- Downloadable issue report generated from `import_candidates.issues`.
- Mapping templates stored in `import_workspaces.config` or exported/imported as JSON.
- Basic import metrics:
  - rows uploaded
  - candidates ready
  - candidates committed
  - unresolved blockers
  - duplicate decisions
  - dependency-blocked candidates
