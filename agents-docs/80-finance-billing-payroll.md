## Currency helpers — mandatory usage
- **All monetary values in the DB and API layer are integers (agorot). 1 ₪ = 100 agorot.**
- Backend: import `coerceAgorot`, `toShekel`, `assertAgorot`, `assertAgorotNullable` from [`../api/_shared/currency.js`](../api/_shared/currency.js).
- Frontend: import `formatCurrency`, `toShekel`, `toAgorot`, `coerceAgorot` from [`../src/lib/currency.js`](../src/lib/currency.js).
- Use `coerceAgorot(value)` when reading any monetary value from the DB or an API response.
- Use `assertAgorot(value, fieldName)` when validating monetary input from a request body.
- Use `toShekel(agorot)` to convert to shekels for display. **Never interpolate a raw agorot integer into a user-facing string.** Build display strings like: `` `₪${toShekel(coerceAgorot(amount)).toFixed(2)}` `` (backend) or `formatCurrency(amount)` (frontend).
- Do **not** write local currency helpers (`roundCurrency`, `formatAmount`, etc.). Use the shared helpers above.
- The `FINANCE_LIMITS` and `BILLING_THRESHOLDS` constants in `api/_shared/currency.js` are the canonical financial guard rails — use them instead of hardcoding limits.

## Known patterns / do not reinvent
- Money is stored and passed as agorot integers.
- Finance policy reads from `Settings` must always be org-scoped (`org_id`) in backend code; service-role reads without `withOrgScope(..., orgId)` can silently pull another tenant's billing policy.
- The append-only ledger is the single source of truth for balances. Do not derive balances from cached lesson fields, commitment totals, or ad-hoc SQL sums.
- The Financials HMO claims read model must be ledger-backed. `ledger_transactions` with active HMO `lesson_charge` rows determine whether a claim exists; `dashboard_tasks` may overlay workflow state (`open` / `resolved`) but must not be the only source used to decide if an HMO claim row should appear.
- `commitments` are removed from the active billing model. Do not add new code that reads or writes commitment balances or commitment-linked lesson billing.
- `ledger_transactions` are immutable. Fixes must be expressed as reversing rows plus replacement rows, never `UPDATE` or `DELETE`.
- Calendar, attendance, HMO authorization, and manual billing endpoints must stay thin. They orchestrate domain changes and then call `BillingLedgerService`; they do not contain billing math or direct ledger SQL.
- Calendar-generated `lesson_charge` rows must not be manually reversed through generic ledger reversal UI/API. Change the calendar lesson/participant status instead so `BillingLedgerService.syncLessonParticipantCharge(...)` can append the correct reversal and avoid a later calendar sync recreating the same charge.
- Student billing uses a `student` ledger account. One-time customers use a `client_profile` ledger account. HMO receivables use an `hmo_provider` ledger account.
- `ledger_accounts` must hold first-class HMO provider accounts (`account_type = 'hmo_provider'`, `hmo_provider_id = provider id`). Do not represent HMO receivables as ledger rows with `ledger_account_id = null`.
- Legacy student `ledger_accounts` rows may exist without `client_profile_id`. Migrations should backfill that link when possible, but schema constraints must not fail solely because a historical student account is missing that column.
- For existing environments, `ledger_accounts` integrity rollout should be staged: add columns permissively, backfill/repair legacy rows, abort with a clear diagnostic if invalid rows remain, and only then add strict validated constraints. Do not rely on looser long-term constraints as the default migration strategy.
- Schema backfills may repair missing HMO `ledger_account_id` links on historical rows, but must not alter financial facts such as amount, direction, source, effective date, or reversal linkage.
- HMO billing now uses a canonical coverage-decision model:
  `hmo_provider_tracks` are templates only and hold defaults for `default_customer_charge_amount`, `default_insurer_claim_amount`, `default_post_coverage_policy`, and `default_post_coverage_customer_charge_amount`
  `hmo_authorizations` are the source of truth for live covered pricing via `covered_customer_charge_amount`, `covered_insurer_claim_amount`, `authorized_lessons`, `post_coverage_policy`, and `post_coverage_customer_charge_amount`
  `resolveLessonCoverageDecision(...)` in [`../api/_shared/hmo.js`](../api/_shared/hmo.js) is the single resolver for `covered`, `post_coverage`, `standard_uncovered`, and `blocked`
  `authorized_lessons` is enforced dynamically from active ledger rows carrying `hmo_authorization_id`; reversal rows restore entitlement
  no finance path may derive customer copay from `service.default_customer_charge_amount - insurer amount`
  `post_coverage_policy = service_default` means fall back to the service list price after entitlement exhaustion
  `post_coverage_policy = explicit_customer_charge` means charge the stored explicit post-coverage customer amount
  `post_coverage_policy = manual_block` means billing must stop with a clear blocked reason after entitlement exhaustion
  overlapping matching active authorizations are treated as a data conflict and billing is blocked until resolved
- Org setting `hmo_non_attendance_billing_policy` controls billable non-attendance statuses (`no_show`, `cancelled_student`, `cancelled_clinic`) for students with HMO coverage:
  `student_private_rate` (default) charges only the student, using the service list price while coverage is active and the authorization post-coverage policy after entitlement exhaustion;
  `hmo_coverage` preserves covered HMO split pricing for those statuses.
- Student/HMO lesson-balance UI must not expose only a single ambiguous "lessons left" number when operational counting matters. Preferred output is the 3-bucket model:
  `consumed_lessons` (`נוצלו`),
  `reserved_lessons` (`מתוכננים`),
  `available_lessons_to_book` (`זמינים לקביעת תור`).
- Student balance top-ups are credit-ledger operations, not package creation. If the UI offers a "lessons × service price" calculator, it must use `Services.default_customer_charge_amount` only as a user convenience and still submit a normal `append_manual_credit` ledger action.
- For HMO authorizations:
  attended covered lessons consume entitlement,
  future scheduled covered lessons reserve entitlement,
  HMO `no_show` never consumes entitlement even if the org bills the lesson privately,
  claim submission/payment status must never change entitlement counts.
- Student billing lesson history may expose `hmo_authorization_usage` per row. Treat it as a read-model explanation only: `consumed` means the lesson counts against the authorization, `planned` means it reserves future capacity, and `not_counted` means the lesson has authorization context but does not affect the HMO lesson buckets.
- HMO invoice batches are workflow metadata only. Balance changes happen only when explicit ledger credits or debits are appended.
- HMO claim lifecycle v2 uses `hmo_invoice_batches` / `hmo_invoice_batch_items` as the operational submission model. New batches are created as `draft`, submitted via `BillingLedgerService.submitHmoInvoiceBatch(...)`, and payments must be recorded against submitted batches via `recordHmoInvoiceBatchPayment(...)`.
- HMO claim batch creation must select active HMO receivable ledger rows, exclude reversed/already-batched rows, include `org_id` on both batch and item inserts, and enforce `hmo_authorizations.authorized_lessons` by selected/submitted claim count, not by paid claim count.
- Cancelled `hmo_invoice_batch_items` are retained for audit. Claim-line reuse must ignore cancelled items and treat only active item statuses (`draft`, `submitted`, `acknowledged`, `partially_paid`, `paid`, `disputed`) from active batches as blocking.
- Before HMO claim-line validation, batch creation should ensure the target HMO provider has a real `ledger_accounts` row and should backfill missing `ledger_transactions.ledger_account_id` links for that provider's historical HMO receivable rows. This repair must remain metadata/account-link only and must not change financial facts.
- For pre-prod/backward compatibility, HMO batch creation may accept `dashboard_tasks.id` values from older UI/read-model payloads, but it must resolve them to active `ledger_transactions` before validation. `dashboard_tasks` remain workflow prompts only and must never be treated as financial claim-line truth.
- `BillingLedgerService.inspectHmoClaimReadiness(...)` is the read-only diagnostic entrypoint for system-admin HMO claim investigations. Use it when an admin needs to understand why a participant or requested claim batch is not claimable; do not build parallel ad-hoc SQL diagnostics in page code.
- Submitted HMO invoice batches create `participant_locks` with `lock_source_type = 'claim_batch'`; workflow readers must resolve those locks against both legacy `claim_batches` and current `hmo_invoice_batches`.
- Payroll, leave, attendance, and instructor earnings rules are read through `loadFinancePolicies` in [`../api/_shared/employee-finance.js`](../api/_shared/employee-finance.js): the plain ones from `Settings`, the money-affecting ones as **dated settings** (below).
- **Dated settings** (owner decision 2026-11-16). A setting that changes how pay is computed is read as of the date it applies to, like a rate: the value for a lesson is the latest version whose `effective_date` is on or before the lesson's local date (`localDateKey(datetime_start)`); for a leave day, the leave day's date. One model for every such setting, in [`../api/_shared/dated-settings.js`](../api/_shared/dated-settings.js):
  - **Registry:** `DATED_SETTING_KEYS` names the dated keys: `instructor_earnings_policy`, `leave_pay_policy`, `leave_entitlement_policy` (how many leave days a year gives; read for a calendar year as of its 31 December, or today for the current year — see [`50-employees-and-instructors.md`](50-employees-and-instructors.md) and `api/_shared/leave-entitlement.js`; `buildFinancePolicies` exposes it as `leaveEntitlementPolicy` / `leaveEntitlementPolicyEffectiveDate`; no migration moved rows; an org without a version gets the default, `fixed` with the 5-day net table since 2026-11-22, and an org with a saved version keeps it). Adding a key is one line there plus a migration that moves its rows (as `migrations/0003_dated_settings.sql` did).
  - **Storage:** `SettingsHistory` (`org_id`, `key`, `effective_date`, `settings_value`, `notes`, `created_by`, `created_at`; unique `(org_id, key, effective_date)`). A dated key is never in `Settings`: `loadSettingsMap` throws if asked for one. The first version of a moved value is effective `2000-01-01` ("since the beginning", as carried-over rates).
  - **One read path:** `loadDatedSettingRows` once per request, `resolveSettingOnDate(rows, key, dateKey)` per date. Finance code calls `loadFinancePolicies(client, orgId, { asOf })` — `asOf` is required; a caller that means "now" passes `todayKey()`. The returned object has the policies on `asOf` plus `onDate(dateKey)`; `financePoliciesOnDate(policies, date)` is how `resolveCountedLesson` (per lesson) and `computeEmployeePay` (per leave day) read them, so one load serves a whole period. `buildFinancePolicies` is the pure builder for tests.
  - **One write path:** `POST`/`PUT /api/settings` with `{ settings: { <key>: { value, effective_date, notes } } }` (or a body-level `effective_date`); `effective_date` is required for a dated key (`missing_effective_date` / `invalid_effective_date`), the value is validated (`validateLeavePayPolicyInput`, `validateInstructorEarningsPolicyInput`, `validateLeaveEntitlementPolicyInput`) and upserted as a version (`saveDatedSettingVersions`, `onConflict: 'org_id,key,effective_date'`; the same date replaces). `DELETE` refuses a dated key. `GET /api/settings` returns a dated key in the usual `settings` map as the version in force on `as_of` (default today), and with `include_versions=1` adds `versions: { key: [{ effective_date, settings_value, notes, created_at }] }` newest first. There is no other endpoint for them; `GET /api/billing` no longer returns `instructor_earnings_policy`.
  - **UI:** every screen that edits a dated key uses [`DatedSettingFields`](../src/features/settings/components/DatedSettingFields.jsx): "בתוקף מ-" (default today), the warnings from `buildDatedSettingWarnings` ([`dated-setting.js`](../src/features/settings/lib/dated-setting.js): a past date recomputes pay already shown; a date before the current version only lasts until it; a date that has a version replaces it), and "היסטוריה (N)". A setting whose past date reaches back differently passes `pastDateWarning`. A screen that saves several dated keys from one date passes `parts` ([{ key, label, versions, describeVersion, changed, pastDateWarning }]): one date, the warnings of each part that will get a version (each with its own past-date wording; `buildDatedSettingsWarnings`), and one history of all their versions, labelled (`mergeVersionHistory`). Today: `LeaveDefaultSettings.jsx` (the one "חופשה" tile, module `leaveDefault`; owner decision 2026-11-17) — a stepped flow: step 1 "כמה ימי חופשה מגיעים בשנה?" (`leave_entitlement_policy`: "כמות קבועה" first, with a table per seniority year prefilled with the 5-day net table, preselected for an org with no version; or "מומלץ: לפי ותק וימי עבודה" — the stored mode `legal`; the UI never says "לפי החוק"), then, once step 1 has a choice, step 2 "כמה משלמים על יום חופשה?" (`leave_pay_policy`: "ממוצע מומלץ" / "ממוצע היסטורי" and the months), revealed by `StepReveal.jsx` (CSS grid rows, no library). The owner's disclaimer (set leave by the contract with the accountant) is at the top. One "בתוקף מ-" and one save: `buildLeaveSettingsVersions` ([`leave-settings.js`](../src/features/finance/lib/leave-settings.js)) writes a version of each key that changed, same date, in one `POST /api/settings` (`saveDatedSettings`); an unchanged key gets none. An organisation with no leave-days version in force today opens with "כמות קבועה" preselected (step 2 shown); its first save always writes a version, even for the preselected choice. Also the "שכר מדריך" part of `BillingSettingsWorkspace.jsx` (through `useInstructorEarningsPolicy`, which adds a version only when the earnings policy differs from the one in force on the chosen date). Back-dating is allowed.
  - **Not dated (yet):** `billing_consumption_policy`, `hmo_non_attendance_billing_policy`, `leave_policy` stay in `Settings`; student billing becomes dated in a later stage. The SQL functions that complete or cancel a lesson no longer read the earnings policy.
- **Pay rules spec (owner-approved, 2026-09-17):** [`../implementations/business-process/payroll-scenarios.md`](../implementations/business-process/payroll-scenarios.md), with the technical plan in [`payroll-prerequisites.md`](../implementations/business-process/payroll-prerequisites.md). Every scenario ID (`PAY-A1` … `PAY-K7`) is in [`../test/payroll-rules.test.js`](../test/payroll-rules.test.js): rules that exist are real tests, rules not yet built are `it.todo`. When you build a rule, turn its todo into a real test first. The key decisions:
  - Rates are dated in `RateHistory`, with a `pay_basis` column: `lesson_hourly` / `lesson_flat` (per service), `attendance_hourly`, `monthly_salary`, `leave_day`.
    - **Pay code reads rates only through [`../api/_shared/rate-history.js`](../api/_shared/rate-history.js)** (`loadRateHistoryRows`, `resolveRateOnDate`, `resolveLessonRateOnDate`, the lesson's date is `localDateKey(datetime_start)` from [`../api/_shared/local-time.js`](../api/_shared/local-time.js), its Israel date). There's no fallback between kinds, and a missing rate pays nothing.
    - Rates are read and written by the office through [`../api/employee-rates/`](../api/employee-rates/) and `src/components/settings/employee-management/EmployeeRatesPanel.jsx` (employee → finance tab). Saving always adds a dated row; a date that already has a rate of that kind needs `replace_existing`. There is no other copy of a rate: the legacy columns and their mirror were removed (`migrations/0002_remove_legacy_rate_columns.sql`).
    - One dialog adds every kind of rate for work: the office picks what the rate is (per service / hourly / monthly) and the fields follow. A lesson rate always belongs to a service; the other kinds never have one.
    - **Pay is additive across kinds** (2026-09-23). `api/payroll` adds every part the employee has rates for — lesson earnings, office hours × `attendance_hourly`, a pro-rated `monthly_salary` — through `combinePayComponents` in [`../api/_shared/employee-finance.js`](../api/_shared/employee-finance.js). There is no pay model: no label, no column. An instructor who also does stable work is paid for both; use `hasRateKind(rows, {employeeId, payBasis})` to ask whether a part exists.
    - Salary coverage is decided **per date** (`computeEmployeePay`): a leave day is covered by the salary only when a `monthly_salary` rate is in force on that date. A covered day is part of the salary ("כלול במשכורת", no leave amount); any other leave day is valued by the leave pay method of that date and added on top. A salaried working day is the salary ÷ the working days of its calendar month, so a full month is exactly the salary. On a covered day: paid full leave pays the day, unpaid leave takes off its unpaid part, and a paid half day pays the full day when work was recorded (a counted lesson or `other_minutes` > 0, the `collectWorkedDates` test) and half a day otherwise, which raises the amber tag "חצי יום חופשה בלי שעות" (`half_leave_without_hours_count` / `_dates`) in the "כספים" table. In the employee summary it is not a separate section: the half day's own line under "חופשה" (`details.leave[].half_leave_without_hours`) carries the same words and, in amber, the deduction that happened (`salary_deduction`, shown "−₪X" with "חצי יום לא שולם") where a fully covered day says "כלול במשכורת"; the detailed print mirrors it.
    - The panel groups the cards by what pays them ("לפי מפגש" / "שכר עבודה"). A service the employee has no capability for is tagged "שירות לא משויך"; nothing is tagged unused, because every kind the employee has a rate for is paid.
    - The employee overview tab shows capacity, payment basis and availability, never a rate figure: rates and their history live in the finance tab only.
    - **A capability carries no money.** `instructor_service_capabilities` has no rate column and the capability dialogs have no rate field. A capability once stored a per-session amount converted to hourly and a trigger copied it into `RateHistory`, so pay changed whenever a lesson's length did; that column, the employee rate columns and every mirror trigger are gone. Never reintroduce a second writer: `api/employee-rates` is the only one.
  - **Pay is computed live, nothing derived is stored.** `api/_shared/pay-calculation.js` is the only place that turns facts into pay (`loadCountedLessons`, `computeEmployeePay`). There is no `lesson_earnings` table, no `payroll_runs`, and no lesson minutes on attendance rows. `employee_attendance_records` holds only `other_minutes` (office work, written only by `api/employee-attendance`); lesson minutes per day are read from the calendar by the same endpoint (`lesson_days`). A changed rate, mark or lesson shows in pay on the next read; never add a sync step or a stored copy.
  - **Leave pay is not a rate for work.** It is a dated method on the employee (`leave_pay_method` versions in `SettingsHistory` with a "בתוקף מ-" date: the legal average, a historical average, or a fixed day value; none or null means the org default on that day), chosen for every employee type as step 2 of the "חופשה" row in the "נוכחות" tab (`EmployeeLeaveSettings.jsx`, see [`50-employees-and-instructors.md`](50-employees-and-instructors.md); the method version is saved with `POST /api/employee-leave { entity_type: 'leave_pay_method_version' }` and step 1's `annual_leave_days`, which is not dated, with `PUT /api/instructors`, only what changes) — not in the finance tab (the old leave-pay box is gone), not in the rates screen and not in `EditEmployeeDialog`. `RateHistory.leave_day` only carries the dated value for the `fixed_rate` method; the same step shows and sets it (`LeaveDayRateEditor` in `EmployeeRatesPanel.jsx`, saved through `api/employee-rates`, its own save).
  - A closed pay month is never reopened; later fixes become pay differences.
  - Whether a participant pays the instructor is the earnings policy in force on the lesson's date (dated settings), unless a person chose otherwise in the absence form: that choice is the only decision stored (`compensated` / `not_compensated` in `lesson_participants.metadata.workflow.instructor_compensation`, via `resolveExplicitInstructorCompensationDecision`) and it overrides the policy for that participant. Nothing is copied from the policy at the mark: a policy change from a date reaches exactly the lessons from that date. Details in [`60-calendar-and-sessions.md`](60-calendar-and-sessions.md).
  - **A missing lesson rate is blocked when a person adds or moves a lesson, never when marking attendance** (owner decision). `validateInstructorRateForLesson` runs on lesson create, on an edit that changes instructor / service / date (including a one-off move to another instructor), and on template create / edit; it returns the `422` body (`code: 'instructor_rate_not_configured'`, `instructor_employee_id`, `service_id`, `rate_date`, `next_rate_date`, Hebrew `message` from `describeMissingLessonRate`). Marking attendance, completing a lesson, template generation and imports are never blocked; such lessons count, pay nothing, and show as "missing rate" until a rate is added. Details and the client flow ("הוספת תעריף" → `AddLessonRateDialog`) are in [`60-calendar-and-sessions.md`](60-calendar-and-sessions.md). Endpoints call it through `checkInstructorRateForLesson` (returns null, the 422, or a 500 with `error` for the endpoint's tracked responder); a move counts as a date change by the lesson's Israel date (`hasLessonPayDateChanged`). Finance corrections (`api/_shared/calendar-corrections.js`) may change the instructor or service without a rate check, deliberately: a correction records what happened, and a missing rate shows in the monthly summary.
  - **Monthly pay summary (stage 6).** One component, [`EmployeePaySummary`](../src/features/finance/components/EmployeePaySummary.jsx), shows one employee's month: the total ("שכר צפוי לחודש"), a row per part that has something ("מפגשים · N", "שעות עבודה · H:MM", "שכר חודשי", "חופשה בתשלום · N ימים", "תיקונים · N") and one exception row only when non-zero ("חסר תעריף" — those lessons are not in "מפגשים" and not in the total). A lesson nobody marked is paid as attended and listed once, where it is: the "מפגשים" row and its service line carry an amber count ("1 לא סומן" / "2 לא סומנו", icon + words), and the lesson line itself has the marker "לא סומן" with its link "למפגש ביומן" (there is no separate "לא סומן אם הגיעו" section, on screen or in print; the all-employees row keeps its "לא סומן: N" tag). Rows open in place, one at a time (button + `aria-expanded`): lessons by service, then a service's lessons; office hours per rate period; leave days; corrections. An unmarked lesson line links to `/calendar?date=YYYY-MM-DD&lesson=<id>` (`CalendarPage` opens that day and the lesson, then clears the params); the missing-rate row offers "הוספת תעריף" (`AddLessonRateDialog`, admin/office only) and reloads after saving. It is used in the employee finance tab (replacing the old live-pay tiles) and under a row of the "שכר" tab on `FinancialsPage` ([`PayrollMonthTable`](../src/features/finance/components/PayrollMonthTable.jsx): one row per employee with total and tags, a total row; the list is one `GET /api/payroll` without details, an opened row reads `details=1` for that employee only).
    - The rows are arranged by the pure module [`../src/features/finance/lib/pay-summary.js`](../src/features/finance/lib/pay-summary.js) (tests: `test/pay-summary.test.js`). It never computes pay: every amount is one the server returned, or a sum of them for a group. Lessons are grouped by (service, `pay_basis`, `service_payment_model`, `rate_used`), one line each, older rate first, and each line is a calculation: per lesson "N מפגשים × ₪rate", per hour "H:MM שעות × ₪rate לשעה", per rider "N רוכבים × ₪rate" (`per_student` with `lesson_flat`), per rider and hourly "H:MM שעות רוכב × ₪rate לשעה" (minutes × paid riders, as `resolveLessonInstructorPayout` multiplies). The line amount is the sum of the server `payout_amount`s; when quantity × rate does not equal it (per-lesson rounding, mixed cases) the "× rate" part is dropped and only the quantity shows. The "חסר תעריף" row is red with `BanknoteX` and "₪0" next to "לא נכלל בסכום"; its tag in the all-employees table is red too. A missing-rate lesson is listed under its exception row, not under its service, so "מפגשים · N" counts paid lessons.
    - `details=1` returns per lesson what `resolveCountedLesson` gives, including `start_time` (Israel time) and `participant_states` (count per state as marked; a participant pay assumed attended is `unmarked`), plus `details.attendance` (date, minutes, `rate_used`, amount), `details.leave` (date, `pay_fraction`, amount) and the top-level `corrections`.
    - Print: "סיכום" / "סיכום עם פירוט" lay the printout out in a hidden iframe with its own document and print that iframe's window (`PrintPortal` in [`PaySummaryPrint.jsx`](../src/features/finance/components/PaySummaryPrint.jsx); styles in [`pay-print-styles.js`](../src/features/finance/components/pay-print-styles.js)), so the printout never shows in the page and no app style reaches it (a `filter` on the app's `<html>`, e.g. the accessibility high-contrast mode, made Chrome print every page as an image). The header has the titles and the print date, Reinex's logo (`/icon.svg`) and the organisation's logo when it has one (`org-logo`), like TutTiud's exports; fonts are installed Hebrew fonts (Arial first) so "Save as PDF" keeps real, selectable text (a downloaded web font came out as Type3 glyphs). Nothing is `position: fixed` (it repeats over the table on every page); the page number is in the `@page` bottom margin box. On the all-employees page, "סיכום" prints the table and "סיכום עם פירוט" reads everyone's details in one request and prints a page per employee.
    - Not built: a warning with the pay difference when a lesson from a month that has ended is marked or edited. `requires_impact_warning` exists only in the correction flow (`api/_shared/calendar-corrections.js`), which a lesson enters only when it is locked by an HMO claim batch; `api/calendar-attendance` and lesson edits have no confirmation step.
  - Legal amounts are dated settings, and closing and exports show a disclaimer.
- Instructor earnings are calculated from the `lesson_hourly` / `lesson_flat` rate in effect on the lesson's date (`RateHistory`).
- Instructor payout now also depends on `Services.payment_model`:
  - `fixed_rate` pays once per lesson
  - `per_student` multiplies by compensation-eligible participant count
- Do not add "rebuild billing" fallback buttons to student/client billing workspaces. Billing recalculation belongs to the mutation source: attendance/session changes, lesson-instance edits, and HMO authorization create/update/cancel already trigger the relevant ledger resync and should communicate that in their own UX.
- Student finance snapshots may include `intake_finance_notice` from a matched waiting-list entry so staff can see the funding path chosen on the intake form. The backend owns the lifecycle: do not return the notice once the student has effective ledger activity, any HMO authorization, or the 30-day post-match window has expired. Frontend dismissal is per browser via `localStorage` only and must not be treated as shared workflow state.
- Student roster finance-source tags are informational only. An active HMO authorization may label the student with the provider; otherwise the student is shown as regular billing. Do not treat missing HMO authorization as a scheduling/generation warning by itself.
